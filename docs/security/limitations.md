# What Relay Does Not Do (System Limitations & Non-Goals)

**Document ID:** `SEC-LIM-001`  
**Version:** `0.1.0`  
**Author:** Principal Security Architect  
**Status:** Authoritative Boundary Statement  

---

## 1. Explicit Non-Goals and Architectural Boundaries

Relay is designed with extreme precision around its specific threat boundary: **local-first deterministic authorization, credential isolation, and cryptographic evidence for AI agents**.

To maintain trust with security engineers and prospective users, this document explicitly details what Relay **does not do** and which threat vectors remain outside its domain.

---

## 2. Comprehensive Limitations Matrix

### 1. Relay Does Not Protect Against a Compromised Host Kernel or Root Attacker
If an adversary has obtained root privileges or executed arbitrary code inside the host OS kernel, they can:
- Read memory pages directly from the Relay process (`/proc/$PID/mem`).
- Modify the running Relay binary or system dynamic libraries.
- Delete or replace the SQLite ledger database on disk.
- Read private keys directly from the filesystem.

**Trust Assumption:** The host operating system kernel and process isolation primitives are trusted.

---

### 2. Relay Does Not Guarantee Remote External System State
An `ActionReceipt` generated by Relay is cryptographic proof of Relay's *observation* (e.g., that Relay sent an HTTP `POST` and observed an HTTP `201 Created` with a specific payload hash). It does **not** prove:
- That the remote database has permanently persisted the write across multi-datacenter replication.
- That a downstream asynchronous cloud job completed successfully.
- That a GitHub administrator did not subsequently delete or roll back the repository.

---

### 3. Relay Does Not Replace Database-Native Access Controls
While Relay enforces Cedar policies over SQL queries (e.g. blocking `DROP TABLE` or write queries), it is **not** a replacement for:
- PostgreSQL role-based access controls (`GRANT` / `REVOKE`).
- Row-Level Security (RLS) policies.
- Database auditing logs.
- Network firewalls protecting the database port.

---

### 4. Relay Does Not Magically Make Insecure Policies Safe
If an administrator configures an overly permissive Cedar policy (such as `permit(principal, action, resource);`), Relay will faithfully authorize and execute all actions permitted by that policy. Relay's security boundary is only as strong as the policies configured by the operator.

---

### 5. Relay Does Not Use Probabilistic LLM Heuristics for Authorization
Relay intentionally avoids "AI-based safety classifiers". Authorization decisions are evaluated purely through deterministic AWS Cedar boolean logic. If an action matches a Cedar rule, it is allowed; if not, it is denied.

---

### 6. Relay Does Not Mediate Direct Out-of-Band Network Access
Relay governs actions invoked through its MCP gateway and native connectors. It cannot prevent an external process or developer terminal from connecting directly to the PostgreSQL database or GitHub API out-of-band without going through Relay.

---

### 7. External MCP Network Egress Boundaries by Platform
Relay mediates external MCP subprocess network egress via an in-process loopback HTTP forward proxy with Cedar allowlisting and vaulted credential injection.
- **On Linux (Full Enforced Sandbox Mode):** Subprocesses are placed inside isolated unprivileged User and Network Namespaces (`CLONE_NEWUSER | CLONE_NEWNET`), preventing 100% of raw socket egress (`ENETUNREACH`) and forcing all traffic through the proxy.
- **On macOS and Windows (Managed Cooperative Proxy Mode):** Relay sets standard environment variables (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `RELAY_PROXY_AUTH`). An adversarial binary executing direct raw socket syscalls without consulting proxy variables bypasses mediation on non-Linux platforms. Hard containment on macOS/Windows requires hypervisor or container virtualization.

---

### 8. Relay Does Not Provide Hardware-Backed Custody by Default
While Relay integrates with the OS Keyring (which may leverage Apple Secure Enclave, Windows TPM, or Linux Secret Service depending on host hardware), Relay itself is software. In headless environments using the encrypted file fallback (`EncryptedFileProvider`), master key security depends on host filesystem and environment variable protections.

---

### 9. Local Security Console Boundaries & Non-Goals (CR002)
The **Relay Local Security Console** (`relay ui`) provides real-time operational visibility over Relay's security boundary:
- **Not a Cloud Dashboard:** The console is strictly local and loopback-only (`127.0.0.1`). It does not connect to external clouds, aggregate fleet metrics, or provide multi-tenant authentication.
- **No Browser Approval Bypass:** Sensitive destructive actions requiring operator approval MUST be confirmed on the controlling terminal (`/dev/tty`). The console displays pending approvals but explicitly provides no browser click mechanism to authorize operations.
- **No Direct Execution Path:** The UI cannot be used as an alternate execution endpoint to trigger tool commands. Tool execution only occurs through governed MCP protocol mediation.
- **Localhost Plaintext HTTP:** By default, the local console serves HTTP over loopback (`127.0.0.1`), assuming kernel-level protection between local processes. It does not provide HTTPS certificates out-of-the-box; for remote access across networks, operators must use an SSH tunnel (`ssh -L`).
